The preview panel is the right-side panel in the Tasklet UI — it can display static file previews, remote computer sessions, or instant apps. Instant apps are the interactive mode: users can click buttons, fill forms, filter data, and navigate between views, all within the preview panel. Instant apps can also connect to the user's external services (Google Calendar, GitHub, Notion, etc.) via the bridge API. --- ## 1. Development workflow Follow these four steps every time you create or update an instant app. ### Step 1: Scaffold with `create_instant_app` **Always start new apps by calling `create_instant_app`** with four arguments: - `name` — filesystem-safe, kebab-case (e.g. `expense-tracker`) - `displayName` — human-readable title for the preview panel (e.g. `Expense Tracker`) - `description` — short summary of what the app does - `type` — `tsx` for React or `html` for standalone HTML/CSS/JavaScript **Infer all four values from the conversation context — do not ask the user.** This scaffolds the full directory under `/tasklet/agent/home/apps//`, including `tasklet.config.json` (the app manifest) and exactly one source entrypoint: `app.tsx` for `type=tsx`, or `index.html` for `type=html`. The manifest's `instantAppType` controls preview behavior. A `tsx` app builds `app.tsx` and generates `index.html`; an `html` app serves the authored `index.html` directly. Do not add the other source entrypoint. For legacy apps whose manifest has no `instantAppType`, preview preserves the old behavior: the presence of `app.tsx` makes the app TSX. ### Step 2: Discover response shapes for connection tools If your app uses **connection-prefixed tools** (e.g. `conn_abc123__google_calendar_search_events`) or other tools not covered by the typed `window.tasklet` methods, call them directly first (as a normal tool call, NOT inside the app) to see the exact response shape. Then add a typed wrapper function in your app code with validation. See [Bridge API](#5-bridge-api-windowtasklet) for details. ### Step 3: Build the app **Plan the file structure first.** For TSX apps, identify the major UI sections (e.g. list panel, detail view, header/toolbar, modals) and create a separate `.tsx` file for each under `components/`. Keep `app.tsx` as a thin shell — state, layout, and imports only. For HTML apps, edit `index.html` and split optional CSS or JavaScript into separate files when useful. Use `window.tasklet` for all bridge calls. ### Step 4: Show the preview **After all code changes, call `show_user_preview`** (with `kind=app` and `rootPath` pointing to the app folder) to build and display the app. This is the step that makes your work visible to the user — editing files alone does nothing. If the build fails (type errors, bad imports, syntax errors), fix the errors and call `show_user_preview` again. Do not report the work as done until `show_user_preview` succeeds. --- ## 2. Project structure The `create_instant_app` tool scaffolds the source type you select. For `type=tsx`, the build system type-checks with `tsc`, bundles with esbuild, and generates `index.html` with DaisyUI/Tailwind CSS from CDN. Dependencies are installed via npm (cached after first build).
